## 一、GitHub 同类项目调研（≥1k ★、近半年活跃）

### 1. liketrek/TREK ⭐14.7k · TypeScript · AGPL-3.0
- **活跃度**：2026-03 创建，今天（10-11）仍在更新；34 open issues。
- **核心功能**：自托管旅行/行程规划器；实时多人协作、交互式地图、PWA、SSO(OIDC)、预算(Budget)、打包清单、照片集成(Immich/Synology)、航班导入(AirTrail)、交通活动、地点搜索(Nominatim)、路线规划。
- **技术栈**：npm/pnpm workspaces 单体仓库（client / server / shared 三层）；前端 **React 19**（强制统一版本）；后端 Node；Docker/Alpine 镜像；sharp 生成图标。DB 推断为 Postgres（自托管标配），实时协作推测走 WebSocket。
- **架构**：React SPA（client）+ Node API（server）+ 共享类型（shared）；Docker 部署；插件式外部集成（照片/航班）。
- **Issue 痛点（按评论数）**：
  - 性能：`#218` Trip tab 在 60+ 地点时严重卡顿（21 评）。
  - 第三方集成脆弱：Immich 集成（`#24` 16评、`#1948` HTTP406 13评、`#341`）、Synology（`#500`）、Nominatim 报错（`#576`）、Google Maps API 失效（`#26`）。
  - 自托管升级痛苦：Docker 升级 v3.1.x 启动失败（`#1221` 12评）、升级报错（`#628`）、v3.3.0 后频繁崩溃（`#1576`）。
  - 路线/显示 bug：住宿间无活动时的路线（`#1297`）、航班线缺失（`#850`）。
  - 登录鉴权：iOS 登录（`#294`）、无法登录（`#280`）、改密码失败（`#318`）、无法建管理员（`#1339`）。
  - 移动端：iOS 15 白屏（`#1028`）。
- **优点 / 缺点**：功能最全、社区最热、协作/预算/打包一体化；**重**（自托管门槛高）、规模大了性能掉、外部依赖多易坏、AGPL 限制商用。

### 2. itskovacs/trip ⭐1.9k · TypeScript · MIT
- **活跃度**：2025-07 创建，2026-10-02 更新；8 open issues。
- **核心功能**：极简 POI 地图追踪 + 行程规划；交互式地图管理 POI、规划多日行程、与同伴协作分享；无遥测/广告；OIDC 鉴权；自带 **MCP server**（AI 集成）。
- **技术栈**：全栈 TS。前端 **Angular 21 + PrimeNG + Tailwind 4 + Leaflet 1.9**（markercluster、contextmenu）；后端 `backend/`（Node/TS，OIDC、REST、本地存储卷）；Docker / docker-compose；transloco 国际化。
- **架构**：Angular SPA + Node API + Docker 卷持久化；`mcp-server` 暴露 AI 接口。
- **Issue 痛点**：
  - 鉴权复杂（最高频）：OIDC state 错误（`#11` 19评、`#184`、`#169` Cloudflare 拦截 PyJWKClient）、"Disable Auth"需求（`#4` 22评，小白想要无鉴权模式）。
  - 移动/UX：仅在滚动条上滚动（`#158` 19评）、移动视觉 bug（`#175`）、状态条溢出（`#179`）、行程表不可滚动（`#75`）、编辑与侧栏同步（`#153`）。
  - 外部地图 API：Google Places API header 变更导致坏（`#160` 17评）、google-search 分类未知（`#227`）。
  - 功能请求：自动日期/筛选/分享（`#21`）、导入 Plus Code（`#18`）、**行程分类不同颜色（`#15`）**、货币标识（`#95`）。
- **优点 / 缺点**：轻量、MIT 友好、地图交互干净、有 AI/MCP 接口；鉴权对小白不友好、移动端 UX 有坑、功能偏少。

### 3. gpxstudio/gpx.studio ⭐1.2k · MDX/TypeScript · MIT
- **活跃度**：2026-10-09 更新；110 open issues。
- **核心功能**：在线 GPX 文件创建/编辑/查看；路线绘制、地图轨迹可视化、地形/3D、导入导出。
- **技术栈**：单体仓库：`gpx` TS 库（解析/操作 GPX）+ `website` **SvelteKit 2**（Svelte 5）。地图：**MapLibre GL 6 + maplibre-gl-geocoder + OpenStreetMap + GraphHopper 路由 + Mapterhorn 地形**；状态：immer + Dexie(IndexedDB 离线)；UI：Tailwind 4 + shadcn-svelte + lucide；Vite 6 + adapter-static（**纯静态站**）；需 MapTiler Key。
- **架构**：纯前端静态站（无后端），GPX 解析库独立，IndexedDB 离线存储，路线依赖外部 GraphHopper。
- **Issue 痛点**：
  - 路线引擎依赖脆弱：`#325` "Road Bike routing unusable since a few days"（60 评！外部路由服务波动）；Strava 热力图（`#11` 137评，功能请求）。
  - 快捷键：macOS 快捷键坏（`#88` 18评）、Safari 冲突（`#31`）。
  - 压缩过激进（`#150`）、地图数据层 OpenHikingMap 限访问（`#364`）、自定义 POI 层 Overpass（`#34`）、PBF 瓦片（`#32`）。
  - 功能请求：保存项目（`#151`）、地图匹配（`#199`）、POI 层（`#7`）、演示模式（`#327`）。
- **优点 / 缺点**：纯前端零后端、静态可托管、地图渲染流畅、MIT；**强依赖外部路由/瓦片服务（一挂全坏）**、键盘/平台特定 bug。

## 二、适配需求的落地方案

### 目标回顾
单文件 HTML（CSS/JS 全内联，双击即开）；输入「地点 + 旅游日期」→ 自动规划；顶部 banner（居中大标题 + 右侧徽章：天数 / POI 数 / 总预算）；下方左=按天时间轴卡片（景点/美食/文化/购物 四色、按时间排序），右=腾讯地图按序打点连线；DAY1/2/3 Tab 切换；点击左侧卡片地图飞到对应位置。视觉参考 Stripe（清爽、柔光渐变）。

### 技术栈选型理由
| 维度 | 三个开源项目 | 我们的选择 | 理由 |
|---|---|---|---|
| 前端框架 | React / Angular / Svelte | **原生 vanilla HTML+内联CSS/JS** | 唯一能严格满足「单一 HTML 文件直接打开、零构建、零安装」的路径；框架都需打包/构建，与需求矛盾 |
| 后端 | Node/Postgres 等 | **无后端** | 单文件静态交付，数据内置，无需服务器 |
| 地图 | Leaflet / MapLibre | **腾讯地图 JSAPI GL（`TMap`，GCJ-02）** | 你附带 skill 的硬性约束（国内合规、坐标系一致）；连线用 `MultiPolyline` 直接按序连 POI，**不调用路由引擎**（规避 gpx.studio 那种「外部路由一挂全坏」） |
| 数据存储 | DB / IndexedDB | **内联 JS 数据对象** | 行程数据内置，离线可用 |

### 关键设计决策（⚠️ 需你拍板，见文末问题）
1. **城市数据策略**（决定「自动规划」如何实现）
2. **天数行为**（日期如何影响展示天数）
3. **地图 Key 处理**（单文件 + 合规 + 安全）

### 模块拆分
- **M1 行程数据模型**：JS 对象 `city → days → POIs`（字段：name / type / time / lat / lng / desc / cost / duration）。坐标在编码阶段用腾讯地图 `travel_guide` / `poi_search` 取真实 GCJ-02 后内置。
- **M2 输入与自动规划逻辑**：place + dates → 匹配/生成 day 计划，驱动 M3/M4/M5/M6。
- **M3 Stripe 风格外壳**：banner（居中大标题）+ 右侧徽章（天数/POI数/总预算）+ 两栏布局 + DAY Tab；柔光渐变 CSS。
- **M4 时间轴卡片列表**：按天渲染、四色分类（景点/美食/文化/购物）、按时间排序、点击 → 触发地图飞入。
- **M5 腾讯地图模块**：init（`TMap.Map`）、按类型着色 `MultiMarker`、按序 `MultiPolyline` 连线、`fitBounds`、`flyTo`、`InfoWindow` 弹窗。
- **M6 预算与统计**：按天/总预算汇总，徽章联动。
- **M7 响应式与健壮性**：移动端堆叠、地图加载失败兜底（无 Key 时提示）、按天清空 marker/线（规避 TREK 60+ 卡顿）。
- **M8 打磨**：动画过渡、空态、示例数据、注释。

### 开发优先级
- **P0**：M1 数据模型 + M3 外壳骨架（先有可看的界面）
- **P1**：M4 时间轴卡片 + M5 地图联动（核心差异点，先打通「卡片 ↔ 地图飞入」）
- **P2**：M2 输入自动规划 + M6 预算统计
- **P3**：M7 响应式/兜底 + M8 打磨

### 借鉴并规避的痛点
- **TREK 60+ POI 卡顿** → 按天渲染、切天清空 marker/线，规模可控。
- **trip #15 分类配色诉求** → 从第一天就内置四色分类，不靠后期补。
- **gpx.studio 路由引擎依赖** → 用「顺序直线连线」而非调用路由 API，零外部路由依赖。
- **TREK/trip 自托管/鉴权/升级痛苦** → 单文件零部署零鉴权，天然规避。
- **TREK/trip 移动端 bug** → 响应式优先，移动端左右堆叠、地图高度自适应。
- **密钥安全（jsapi-guide 强制）** → 不硬编码 Key 到公网；采用「页面内 Key 输入框 / 代理」方案并附安全提示。
