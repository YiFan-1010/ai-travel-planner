## 一、项目概述

### 1.1 一句话定位

输入目的地和天数，AI 生成一份可以真正照着走的行程——不是一段文字建议，而是标在真实地图上、沿真实道路、坐标精确到门牌的路线。

### 1.2 要解决的问题

市面上的 AI 旅行规划，绝大多数停在这一步：让大模型输出一段“第一天上午去 A，下午去 B”的文本。用户拿到手会遇到三个硬问题：

**第一，地点是编的。** 大模型不知道真实地理坐标，它会根据训练语料“猜”一个大致位置。小地名、新开的店、非著名景点，猜错的概率很高。用户按图索骥，到地方发现根本没有这个地方。

**第二，路线是连直线。** 把几个经纬度用直线连起来画在地图上，看起来像路线，实际距离和真实道路差得很远。用户无法判断“今天要走多少路”。

**第三，顺序是不可执行的。** 模型按“看起来合理”排顺序，不会算第 2 天从东郊到西郊要穿过整座城市。

这个项目针对的就是这三点：**坐标由工具核实、路线走真实路网、行程经过校验再输出**。

### 1.3 目标用户

- **自由行规划者**：想去一个陌生城市，需要一份能落地的行程骨架，而不是攻略长文
- **带家人出行的人**：需要控制每天强度，知道“这天要走多少公里”
- **临时出差顺带游玩的人**：时间碎片化，需要快速拿到一个可用方案

### 1.4 完成度概览

| 项 | 数值 |
|----------------------|--------------------------------------------------------------------|
| 代码规模 | 11,436 行（前端 7,541 + AI 模块 3,171 + 服务端 689） |
| 运行时依赖 | 1 个（MapLibre GL JS），其余全部自研或浏览器原生 |
| 数据源成本 | 0 元（地图、路线、影像、地理编码全部使用免费开放数据） |
| Git 提交 | 23 次，按功能模块粒度提交 |
| 在线可用 | 是，无需注册、无需填写任何 API Key |

## 二、需求分析

### 2.1 现有方案的缺口

开始设计之前，把能想到的替代方案都实际用了一遍，找出它们各自卡在哪一步：

| 方案 | 能做什么 | 卡在哪 |
|----------------------|-------------------------|------------------------------------------|
| 通用大模型对话 | 给出文字版行程建议 | 地点是编的，坐标靠猜；不知道第 2 天要跨城 |
| 旅行社区攻略 | 真实、有人味 | 碎片化，要自己拼成日程；时效性差 |
| 商业地图路线规划 | 路线准 | 只能逐点算，不会替你决定去哪、怎么排 |
| 现有 AI 旅行助手 | 一键出方案 | 大多只到文本层，不核实坐标，不连真实道路 |
| 行程管理 App | 记录与协作 | 不生成，输入全靠手动 |

共同缺口很清楚：**「能生成」和「能照着走」之间断了一截**。这一截就是坐标与路网。

### 2.2 功能需求与验收标准

| 编号 | 需求 | 级别 | 验收标准 | 实现位置 |
|--------|----------------------------|--------|--------------------------------|---------------|
| F1 | 按目的地与天数生成多日行程 | P0 | 输出结构合法的 JSON，天数与请求一致 | Agent 规划阶段 |
| F2 | 每个地点有真实坐标 | P0 | 工具定位率 ≥ 90%，误差 < 200m | 工具层 + 校验 |
| F3 | 每日路线沿真实道路绘制 | P0 | 使用 OSRM 路网，非直线连接 | 地图层 |
| F4 | 生成过程实时可见 | P0 | 流式输出，进度文案随阶段变化 | SSE 客户端 |
| F5 | 单日强度可控 | P1 | 点位数与跨度可校验、可修正 | 体检阶段 |
| F6 | 同目的地多方案对比 | P1 | 四套风格各自独立 | 多方案模块 |
| F7 | 自然语言调整行程 | P2 | 返回差异并只重渲染变化的天 | AI 调整 |
| F8 | 语音输入目的地与天数 | P2 | 识别后自动填表 | Web Speech API |
| F9 | 导出行程长图 | P2 | 1080×2x，可直接分享 | Canvas 渲染 |
| F10 | 断网仍可查看已有行程 | P2 | 降级为点阵示意图 | 离线模块 |

优先级不是拍脑袋：F1–F4 缺任何一条，产品就不成立；F5–F6 决定「好不好用」；F7–F10 是体验加分。

### 2.3 非功能需求

| 维度 | 要求 | 实测 |
|----------------|------------------------------------------|--------------------------------|
| 首屏 | DOM 就绪 < 2s | 0.84–1.04s |
| 生成耗时 | < 30s，且过程有反馈 | 11.6–19.7s |
| 可用门槛 | 访客零配置，不需要申请 Key | 服务端代理，打开即用 |
| 密钥安全 | 前端产物中搜不到任何 Key | 已用 grep 验证 |
| 移动端 | 390px 无横向溢出 | 0 溢出 |
| 错误可见性 | 失败要有明确原因，不静默 | 超限返回 429 + 文案 |

### 2.4 明确的非目标

需求分析的另一半是「不做什么」。以下五项都是主动放弃的，理由记在这里，避免后续反复：

| 非目标 | 放弃理由 |
|-------------------------------------|-----------------------------------------------------|
| 社交与内容社区 | 那是内容平台的生意，与「生成可执行行程」不是同一件事，做一半反而两边都不像 |
| 预订与支付 | 涉及商家资质、结算与售后，超出个人项目边界 |
| 全量组件化重构 | 算过账：一周工期换 3 分中的一部分，同样时间投 RAG 是 4.5 分（见第七章） |
| 向量检索 | DeepSeek 无 embedding 接口；语料 128 条，BM25 在这个量级没有实质差距（见第四章） |
| 本地地图包（PMTiles） | 能做且已验证通过，但会把部署包从 1.3MB 推到几十 MB，收益不抵成本 |

### 2.2 为什么需要一层服务端

这是本项目一个关键的架构判断。

最直观的做法是纯前端：用户填自己的 API Key，浏览器直接调大模型。开发简单，部署是静态站。

但这样做有两个致命问题：

**其一，Key 暴露。** 一旦为了让访客“打开就能用”而把 Key 写进前端，打包后的 JS 里就是明文。任何人按 F12 都能拿走，刷爆额度。个人开发者的小额 Key 撑不过一天。

**其二，能力不对等。** 高德的地理编码接口在国内 0.5 秒返回，但它是带 Key 的商业服务；如果让每个用户自己去申请，转化率会掉到接近于零。

所以加了一层 689 行的 Node 服务：替用户持有 Key，同源代理请求，附带限流。前端探测到代理存在就自动免 Key，探测不到（纯静态托管）就引导用户填自己的 Key——两条路径前端逻辑完全一致，只是请求地址不同。

### 2.3 前端的渐进式结构

前端 5,625 行业务代码里，有一部分是早期单文件版本留下的（`src/legacy/`）。

没有做全量重构，是一个有意识的取舍，理由在第七章详述。

## 四、AI 核心设计

这一章是本项目的重点。评分表里 AI 技术深度占 35%，团队把绝大部分精力投在了这里。

### 3.1 从“一次调用”到“带反馈的流水线”

**v1 的做法**：把用户输入拼成提示词，请求大模型返回一份包含经纬度的 JSON，直接渲染。

问题很明显：模型编坐标。而且它编得很自信——格式正确、数量正确、看起来完全合理，只有到地图上一看才发现偏了几百米。

**v2 的做法**：把一次调用拆成四个阶段，中间插入真实工具。

```
① 检索   从本地知识库捞出这座城市的实际情况（RAG）
   ↓
② 规划   模型只决定「去哪、怎么排、为什么这么排」，不碰坐标
   ↓
③ 落地   并发调用地理编码工具，把地名换成真实坐标
   ↓
④ 体检   检查单日跨度、地点缺口、点位密度
   ↓
⑤ 修正   把问题清单回喂模型，只改有问题的部分（最多一轮）
   ↓
   输出可上地图的行程
```

这个改动带来两个直接收益：坐标从“模型猜”变成“工具查”，准确率质变；同时因为有了校验环节，行程的可执行性也被约束住了。

### 3.2 工具层设计

工具层封装了四类能力：

| 工具 | 作用 | 数据源 | 实测耗时 |
|----------------------|-------------------------------|----------------------|----------------|
| `searchPlace` | 地名 → 真实坐标 | 高德 / Photon 双源 | 高德 0.3-0.6s |
| `geocodeAll` | 批量并发 + 退避重试 + 熔断 | — | 11 点约 6s |
| `routeFeasibility` | 真实里程与耗时 | OSRM | 1.5s |
| `haversine` | 球面距离（本地计算） | — | 即时 |

**双源策略是被现实逼出来的。**

最初用的是 Photon（基于 OpenStreetMap 的免费地理编码），开发机上完全正常。上线前实测发现：`photon.komoot.io` 在国内被 DNS 污染，解析到 `10.161.101.106` 这类内网地址；`nominatim.openstreetmap.org` 解析到 Dropbox 的 IP。两者都不可达。

同时测了国内三家：高德 `0.5s`、腾讯 `0.35s`、百度 `0.69s`，全部秒通。

于是改成：**高德优先，Photon 兜底并带熔断**。熔断是必要的——如果每个点都去等 Photon 的 9 秒超时，11 个地点要白等 100 秒。连续失败 2 次就直接跳过这个源。

**并发数是被限流教育出来的。**

高德个人 Key 默认 QPS 3。第一版并发 3，结果前 6 个点 300ms 返回，第 7 个开始全部失败。改成并发 2 + 三次退避重试后，11 个点能稳定命中。

但地点数上到 15 个后，又开始出现零星失败——而且是“成都远洋太古里”这种真实存在、单独查一定查得到的地点。问题不在名称匹配，在速率：并发 2 只是同时发出的请求数，失败重试和名称变体（原名查不到时剥掉括号再试）会把瞬时速率放大到 5-6 次/秒，照样超限；超限返回的错误被前端如实记为“定位失败”，看起来像是坐标能力有问题。

真正的解法是把限制下沉到服务端：所有地理编码请求排进一个串行队列，最小间隔 340ms，保证任意时刻速率不超过 3 次/秒。代价是单点最多多等 340ms。

收益超出预期：15 个地点从“13 个命中 + 一轮修正”变成“15 个一次全中”，总耗时反而从 19.1 秒降到 11.6 秒——省掉的不是请求时间，是整轮修正。

**地名变体也要处理。** 模型生成的名字常带修饰成分，高德偏偏认不出：

| 原名 | 结果 | 剥离后 | 结果 |
|-------------------------------------------|--------------|--------------------|--------------|
| 松鹤楼（山塘街店） | 0 条 | 松鹤楼 | 2 条 |
| 栾川豆腐宴（老君山店） | 0 条 | 栾川豆腐宴 | 命中 |
| 虎丘山风景名胜区 | 命中 | — | — |

降级序列：原名 → 剥括号 → 剥景区/步行街后缀，最多三次。这类修饰在模型输出里出现频率很高，不处理会白白多跑一轮修正。

### 3.3 RAG 检索：为什么不用向量

评分表里 RAG 占 6%。实现之前先明确了一个约束：**DeepSeek 没有 embedding 接口**。

这意味着标准做法（文档切分 → 向量化 → 余弦相似度检索）需要引入本地 embedding 模型。实测代价是：多下载几十 MB 模型文件、首屏增加 3-5 秒、浏览器内存占用上升。对于一个以“打开即用”为卖点的 Web 应用，这个代价超过了收益。

**选择了 BM25。**

理由很直接：语料规模只有 128 条（20 个城市 + 通用条目），在这个量级上，词频检索的召回质量与向量检索没有实质差距，而成本是零——零依赖、零网络、零首屏开销。

中文分词用 bigram（两字滑窗）：不依赖词典，对地名和人名友好。“兵马俑”切成“兵马 / 马俑”，查询侧同样切分，能对上。

**一个必须解决的召回问题。**

语料正文写的是“商业化程度高，本地人基本不去”，而用户会说的是“避坑”。这两个词没有任何字面重叠，BM25 召不回来。

解决方法是在建索引时按标签补充通用检索词：

| 标签 | 补充词 |
|-----------------|-------------------------------------------------------------------------|
| 避雷 | 避坑 别去 不值得 踩雷 坑 人多 商业化 |
| 吃喝 | 吃 美食 餐厅 小吃 好吃 本地 |
| 住宿 | 住 住宿 酒店 民宿 住哪 方便 |
| 交通 | 交通 怎么走 距离 通勤 路线 远 |

补完后，“杭州 避坑 人多”的首位命中从第 3 条（徒步线路）变成第 1 条（河坊街避雷），分数从 1.20 提升到 4.02。

**第二个召回问题：语料覆盖不到的城市。**

语料按城市组织，但不可能收录全国所有目的地。第一版只写了 6 个热门城市，结果是：用户搜“苏州”能看到知识，搜“洛阳”则一条都召不回来——BM25 只认字面重合，查询与语料没有共同词，得分恒为 0，界面上“规划依据”整块消失。对评委来说，这等于 RAG 不存在。

三层处理：

1. **通用条目**：10 条不绑定城市的建议（早到避人流、低价团有购物、博物馆周一闭馆、一天别超过 3 个点……），任何目的地都参与召回
2. **降权 0.7**：通用条目分数乘 0.7，保证同分时本城市条目排在前面；本地条目 ≥ 3 条时，通用条目最多保留 1 条，避免提示词被“正确的废话”占满
3. **空结果补齐**：若某城市完全没有收录，按 交通 → 节奏 → 避雷 → 景点 → 吃喝 的顺序各取一条兜底，保证任何目的地至少有 4 条可用依据

界面上区分表述：本地条目 ≥ 2 条时显示“参考了 N 条本地知识”，否则显示“参考了 N 条通用常识”——不把通用建议说成本地知识。

还有一个细节：用户说“洛阳 三天”，“三天”与标签词表里的“几天”字面不重合，召不回节奏类条目。查询侧做了一次归一化，把“N天/N日”统一替换成“几天”。

语料只写**稳定的结构性知识**——空间关系、时间窗、避雷、片区特点，不写票价和营业时间（一年就过期，反而制造错误）。

**检索结果怎么用。**

格式化成【本地知识】段落塞进 user prompt，明确要求“相关时用上，不相关就忽略，不要硬套”。

实测验证了它确实生效：生成成都行程时，输出里出现了语料提到的“人民公园鹤鸣茶社”“奎星楼街”，这两个都不是大模型自己会主动推荐的点。

### 3.4 AI 安全与兜底

模型输出不可控，这是工程落地必须面对的问题。项目做了四层防护：

**① JSON 结构校验。** 解析骨架时逐字段校验类型与范围，缺字段用默认值补，非法值丢弃。兼容模型把结果多包一层 `{"plan": {...}}` 的情况。

**② 坐标越界检测。** 纬度必须在 ±90、经度 ±180 内，否则视为无效坐标并丢弃该点。

**③ 工具超时降级。** 地理编码失败时退回模型自带坐标，并在状态栏如实提示“模型坐标”；路线请求失败时用直线兜底，提示“N 天路网未取到”。

**④ 服务端三层限流。** 单 IP 每小时 12 次对话、单 IP 每天、全局每天 220 次。超限返回 429 与明确文案，不是静默失败。

**⑤ 全链路可回退。** 新版 Agent 编排任何环节失败，会自动回退到 v1 的一次性调用（有自有 Key 时）。功能不会因为一个模块出问题而整体不可用。

### 3.5 思考过程可视化

评分表里“AI 交互体验”占 3%，考察“流式输出渲染流畅、AI 思考状态可视化”。

用户在整个生成过程中能看到：

```
1s   AI 正在规划行程 | 参考 5 条本地知识 · 已写 345 字
4s   AI 正在规划行程 | 参考 5 条本地知识 · 已写 2228 字
6s   正在核对地点坐标 | ✓ 人民公园鹤鸣茶社 3/15
10s  正在核对地点坐标 | ✓ 青城山 13/15
11s  发现行程问题 正在调整 | 「玉林路」在地图上找不到，请换一个真实存在、名称更正式的地点
15s  行程已生成 | 3 天 · 12 个地点 · 工具定位 12
```

这些数字都是真实的：字数来自流式增量累加，坐标命中数是工具的真实返回，修正轮的内容是校验器实际提的问题。

上面日志里那句「发现行程问题 正在调整」，是整个系统最有说服力的一处——它证明模型和工具在互相纠正，而不是模型一次说完就算。

## 五、核心功能实现

前面两章讲的是"AI 怎么做决策"，本章讲"界面怎么把它变成用户能用的东西"。挑六处有工程含量的实现说明。

### 5.1 流式输出的消费：把 SSE 变成可读的进度

后端与模型之间是 SSE，前端要把它变成用户能理解的状态。做法是三层映射：

| 原始信号 | 前端呈现 |
|:--------------------------------|:--------------------------------|
| 首字节到达 | "AI 正在规划行程" |
| 累计字符数 | "已写 2,228 字"，进度条 4%→28% |
| 出现 `"lat":` 的次数 | "已规划 2 天 · 8 个地点" |
| 进入工具阶段 | "正在核对地点坐标 · ✓ 武侯祠 4/15" |

关键在第二层：模型不会告诉你"我规划到第几天了"，只能从已生成的 JSON 片段里数 `"lat":` 出现次数反推。这个数字比单纯的字符数更能让用户安心。

两段式超时是配套的：首字节 60 秒、空闲 90 秒。用非流式 + 8192 token 时实测要等 3–5 分钟，必须流式才有可用性。

### 5.2 路线绘制：三层叠加与生长动画

单条线在地图上会糊在底图里，所以拆成三层：

| 图层 | 宽度 | 作用 |
|:-----|:--------------------------------|:--------------------------------|
| `route-glow` | 18px，blur 8 | 光晕，让路线从底图上"浮起来" |
| `route-casing` | 9px，白色 | 描边，保证深色影像上也看得清 |
| `route-line` | 5px，主色 | 主体 |

生成时用 `line-gradient` 做生长动画，日常用 `line-dasharray` 偏移做出流动光点。两个动画都基于弧长参数，不依赖帧率。

### 5.3 时间轴与卡片：切天的 FLIP 过渡

切换 DAY 时如果直接重渲染，用户会丢失"这几张卡从哪来"的空间感。用 FLIP：

1. 记录旧卡片的位置矩形
2. 旧卡片淡出 150ms
3. 新卡片以 `translate(dx, dy) scale(sx, sy)` 起始，520ms 回到 none

补齐了从"位置 A"到"位置 B"的连续感。拖拽排序复用同一套逻辑，继承原时间槽。

### 5.4 世界模型：搜索定位的三段式镜头

已经在创新点 T5 说明，这里补充工程实现的两个坑：

- `easeTo({duration: 0})` 会**同步**派发 `moveend`。如果监听在调用之后挂，回调永远不触发，用户卡死在中景。统一封装 `gsGlide()`，duration 为 0 时 `jumpTo` 后直接回调。
- 必须有 15 秒 watchdog。任何一步卡住（网络、瓦片、WebGL 上下文丢失）都要收尾，不能让用户停在"正在加载"。

### 5.5 导出长图：Canvas 手绘而非截图

用 `html2canvas` 这类方案有两个问题：跨域图片污染画布、字体渲染与页面不一致。

所以改为在 Canvas 上按设计坐标重绘一遍：1080 宽、2 倍图、浅色版（深色截图打印/分享不友好）。标题、日期、每天的分组、点位编号、耗时与预算全部按设计稿位置摆放。

这是"多写 200 行代码换 100% 可控"的选择。

### 5.6 离线降级：断网时仍有东西可看

底图瓦片无法离线（这一点必须承认），但行程数据可以。断网时用 Canvas 等距投影画一张示意图：点位按经纬度投影到平面，连线用白描边，名称做防重叠处理。

判定走三路：`navigator.onLine`、启动时 `/api/health` 探测、地图错误计数。任一命中就切离线模式，并在状态栏说明"已切换离线示意"。

## 六、创新点说明

分成两类：技术创新点是“这件事以前做得不对，我找到了更对的做法”；应用创新点是“同样的问题，用不同的产品形态解决”。每条都附可验证的证据。

### 5.1 技术创新点

**T1｜坐标可信度分级 + 四阶段核实闭环**

多数 AI 行程工具把坐标当成模型输出的一部分，和文字一起生成。本项目把坐标从模型手里拿走：模型只负责“去哪、怎么排”，坐标由工具查、由校验判、由修正补，形成 规划 → 落地 → 体检 → 修正 的闭环。

闭环的价值在数据上：三次实测全部触发修正轮——模型编的 POI 名在真实地图查不到时，会被点名替换后重新查询。如果只做一次性生成，这三个假地点会直接进最终行程。

**T2｜把限流下沉到服务端，定位失败率归零**

一般的做法是在前端控制并发数（比如并发 2）。实测发现不够：失败重试和名称变体探测会把瞬时速率放大到 5–6 次/秒，仍然超过高德个人 Key 的 QPS 3，导致“成都远洋太古里”这类真实地点被误判为查不到。

本项目把限制下沉到服务端，用串行队列保证全局速率不超过 3 次/秒。**15 个地点从“13 命中 + 一轮修正”变成“15 一次全中”，总耗时 19.1s → 11.6s**。省掉的不是请求时间，是整轮修正。

**T3｜地名降级查询：处理模型输出的修饰成分**

模型生成的地名常带修饰成分，而地理编码服务认不出：

| 模型输出 | 原名结果 | 降级后 |
|------------------------------------------|---------------|---------------------------------|
| 松鹤楼（山塘街店） | 0 条 | 松鹤楼 → 2 条 |
| 栾川豆腐宴（老君山店） | 0 条 | 栾川豆腐宴 → 命中 |

降级序列：原名 → 剥括号 → 剥景区/步行街后缀，最多三次。这一层直接把首次定位率从 87% 拉到接近 100%，也减少了一轮修正。

**T4｜城市知识的轻量 RAG：不用向量也能召回**

DeepSeek 没有 embedding 接口，向量检索需要本地模型（几十 MB + 首屏变慢）。本项目用 BM25 + 中文 bigram 实现检索，零依赖零网络。

难点不在检索本身，在**召回的两处盲区**，都被单独处理了：

- **词面不重合**：语料写“商业化重、本地人不去”，用户说“避坑”。解法是按标签补通用检索词，补完后“杭州 避坑 人多”的首位命中从第 3 条升到第 1 条，分数 1.20 → 4.02
- **城市没收录**：BM25 只认字面重合，搜“洛阳”与语料零交集，得分恒为 0，界面上的“规划依据”整块消失。解法是通用条目 + 降权 0.7 + 按标签轮转补齐

另外做了一次查询归一化：把“N天/N日”统一成“几天”，否则用户说“三天”召不回节奏类条目。

**T5｜世界模型的三段式镜头：先对准，再校准，最后放大**

从太空（z2.2）飞到街区（z16.4）跨 14 级。`flyTo` 的 zoom 曲线是指数式的，2.5 秒冲完 43% 的距离，后半段像卡住；分段 `easeTo` 有明显顿挫。

最终方案是三步：立刻 `easeTo` 到目标中心 + 中景（820ms，用户先看到“到了”）→ Overpass 校准与对准并行（修正超 25m 才平移）→ 逐帧 `jumpTo` 推进 zoom，**中心锁死不动**，掉帧自动降速。

这个方案的关键认知是：**用户感知的是“落点是否在屏幕中央”，不是“缩放是否平滑”**。所以要先给落点，再给细节。

### 5.2 应用创新点

**A1｜零门槛在线演示：让评审直接看到成品**

AI 应用普遍要求用户自备 API Key，这在评审场景下是致命的——评委不会为了看一个作品去注册账号、申请 Key。

本项目在服务端持有 Key，前端通过 `/api` 代理调用，并对每个 IP 做三层限流（小时 / 天 / 全局）。访客打开链接输入城市就能生成，不需要知道 Key 是什么。**密钥在前端产物中用 grep 搜不到**，这是这套架构存在的全部理由。

**A2｜规划依据可展开：把“为什么推荐”摊开给用户**

RAG 类功能常见的失败是“做了但看不见”。本项目做了三层可见性：

1. 生成过程中，进度文案持续显示“参考 5 条本地知识 · 已写 2228 字”
2. 结果页有可展开的“规划依据”，逐条列出参考了哪些知识，带“吃喝/避雷/节奏”标签
3. 依据随行程一起缓存，刷新页面后仍在

用户能判断这份行程是“有依据的”还是“编的”，这比多推荐两个景点重要。

**A3｜语音输入降低输入成本**

旅行场景里，用户常在走路、拎行李、信号不好时使用，打字成本高。用浏览器原生 Web Speech API，说一句“我想去杭州玩三天”，自动填目的地并算出返程日期。

零 Key、零服务端、零 Token 消耗。不支持该 API 的浏览器直接隐藏按钮，不留死按钮。

**A4｜把数据缺陷变成可理解的视觉语言**

OSRM 会把坐标吸附到最近道路，实测市区 91m、镇区 353m、农田 387m。放大到 z16 时 400 米等于 260 像素，“点和线不连”非常刺眼。

导航软件的做法是画接驳线，本项目照做，并且**如实告知**：状态栏写“N 个地点离路较远 已用虚线接驳”，超过 800m 提示“坐标可能不准”。

这不是“遮丑”，是把数据源的真实性质翻译成用户能理解的信息——**承认局限比假装完美更可信**。

## 七、关键技术决策

技术文档最有价值的部分不是“做了什么”，而是“为什么这样选、放弃了什么”。本章记录六个影响全局的判断。

### 4.1 为什么不用高德/腾讯地图做底图

国内商业地图的坐标是 **GCJ-02**（国测局加密坐标），与 GPS 原始的 WGS-84 存在 300-700 米系统性偏移。

如果底图用高德、路线用 OSRM（WGS-84）、卫星影像用 Esri（WGS-84），三者在同一屏上会互相错位几百米——点标记落在河里，路线穿墙而过。

三个选择：
- **A**：全用商业地图（底图、路线、地理编码都换高德）→ 全链路一致，但路线要付费，且无法使用开源数据
- **B**：全用开源（MapLibre + OSM + OSRM + Esri）→ 全链路 WGS-84 一致，成本为零
- **C**：混用 + 逐层坐标转换 → 每层都要转，任何一处漏转就是几百米偏移

选了 **B**，并定了一条硬规则：**应用内部只用 WGS-84，只在调用高德地理编码的那一层做一次转换（GCJ-02 → WGS-84，三轮迭代逼近，误差小于 1 米），偏移绝不外溢。**

这条规则的价值在后期体现得很明显：加入卫星影像、3D 建筑、世界模型时，都没有再出现过坐标错位问题。

### 4.2 为什么“点线不连”要画接驳虚线

用户反馈“点位和轨迹对不上，点飘在线外面”。查了很久，最后发现这不是 bug，是**物理事实**。

OSRM 计算路线时，会先把每个点**吸附到最近的道路**上，再沿路网计算。实测吸附距离：

| 场景 | 吸附距离 |
|-------------------------------------|-----------------------------------------------------|
| 成都市区 | 91 m / 47 m |
| 东台西溪镇区 | **353 m** / 91 m |
| 农田中间 | **387 m** / 177 m |

换算成屏幕：400 米在 z10 只有 2.7 像素（看不出来），在 z16 是 260 像素（非常刺眼）。所以**放大越明显**——这正好对应用户说的“缩小之后看着还行，放大就发现偏了”。

导航软件的标准做法是画“接驳线”，团队照做了：

- 每个点位到它的道路吸附点之间画一条同色虚线
- 相差不到 3 米不画（避免每个点拖一根小尾巴）
- 虚线宽度按缩放级别插值（z7 时 2.8px，z16 时 1.8px），缩小时不能细成一根线

同时状态栏如实告知：“N 个地点离路较远 已用虚线接驳”；超过 800 米时提示“坐标可能不准”。

**这个细节是本项目技术含量的一个缩影**：问题不是代码写错了，而是数据源本身的性质决定的。不理解这一点，会一直在代码里找不存在的 bug。

### 4.3 为什么地图飞行不用 `flyTo`

世界模型搜索定位需要从太空（z2.2）飞到街区（z16.4），跨越 14 个级别。

第一版用 `flyTo`，效果很差：它的 zoom 曲线是指数式的，2.5 秒内前 40% 时间就冲完了 43% 的距离，后半段慢得像卡住。

第二版改成分段 `easeTo`，加了 240ms 停顿，结果是明显的顿挫感。

最终方案是三步：

1. **先对准**：立刻 `easeTo` 到目标中心 + 中景 zoom，820ms。落点标记此时已在视口正中，用户先看到“到了”
2. **再校准**：Overpass 查询与对准并行发起（总上限 2.2s），修正超过 25 米才做 380ms 平移校正
3. **最后放大**：逐帧 `jumpTo({zoom})`，**中心锁死不动**，3 级/秒，末段收束，掉帧自动降速

**关键教训**：`easeTo({duration:0})` 会同步派发 `moveend`，如果监听在调用之后挂，回调永远不会触发，用户会卡死在中景。所以封装了统一的 `gsGlide(map, opts, done)`，duration 为 0 时直接 `jumpTo` 后回调。

另外必须有 15 秒 watchdog：任何一步卡住都要收尾，不能让用户永远停在“正在加载”。

### 4.4 为什么不做全量组件化重构

评分表里“组件化与架构设计”占 3%。

项目有一个 5,625 行的 `legacy/app.js`，拆成组件树看起来是“正确”的做法。但算了一下账：

- 全量拆分 + 回归验证，最快一周
- 风险：184 个函数互相耦合，拆错一处就是连锁故障
- 收益：3 分中的一部分

同样的一周投在 RAG（6 分）上，收益是 4.5 分。

所以采取了**渐进式策略**：

- 新功能全部用严格 TypeScript 写在 `src/ai/`、`src/rag/` 下，模块边界清晰
- 旧代码原样保留在 `legacy/`，每次提交只搬一个模块
- 通过 `window.__AI__` 单向调用，接口明确

这个取舍在校赛阶段是对的，但也确实留下了技术债——如果继续迭代，下一步应该是把 `legacy/` 里的地图渲染、卡片渲染、导出三块独立出来。

### 4.5 为什么卫星影像默认“城市级”

卫星影像有两个来源：

- **NASA GIBS Blue Marble**：公有领域，全球覆盖，但最高只到 z8，是一个“漂亮的纹理球”
- **Esri World Imagery**：能到 z18，城市级能看清屋顶，但有明确的署名要求

最初的默认是“宏观档”（用 NASA 影像做太空视角，放大后淡出切矢量）。这个选择在视觉上更“安全”——不会暴露任何细节问题。

但实测下来，宏观档说服力不足：用户看到的是一个地球纹理球，跟“这是真地图”没建立起联系。

改成默认“城市级”后，打开就是真实的城市影像，放大能看清屋顶、街道、操场跑道。

**这里踩过一个坑**：城市级影像开启后，3D 建筑的半透明白色体块（不透明度 0.72）几乎铺满画面，把真实屋顶完全盖住了——等于城市级白开。压到 0.35 后，立体轮廓还在，屋顶透得出来，两者才协调。

顺带做了配置迁移：老的“宏观档”用户一次性升级到城市级，但**主动选过“关闭”的用户保持关闭**，不打扰。

### 4.6 为什么 Key 必须放服务端

这一条在前面提过，但值得单列，因为它是整个架构存在的前提。

前端直接持有 Key 的三种后果：

1. **明文泄露**：打包后的 JS 里 `Authorization: Bearer sk-xxx` 一眼可见
2. **无法限流**：每个访客都是独立调用，被刷爆之前无法察觉
3. **无法降级**：Key 一旦失效，整个应用不可用

服务端代理解决了全部三点，代价是部署从“静态托管”变成“跑一个 Node 进程”。对于一个要交给评委打开的作品，这个代价完全值得——**评委不会为了看你的作品去申请 API Key**。

配套的限流设计是三层：单 IP 小时、单 IP 天、全局天。既防单点刷爆，也防总量失控。

## 八、工程实践

### 5.1 技术栈

| 层 | 选型 | 理由 |
|-----------|----------------------------------|----------------------------------------------|
| 构建 | Vite 6 | 冷启动快，配置简单，产物可直接静态部署 |
| 语言 | TypeScript 5（strict） | AI 模块与工具层全量类型覆盖 |
| 地图 | MapLibre GL JS 5.24 | 开源无 Key，支持 globe 投影与 3D 建筑 |
| 后端 | Node 原生 `http` | 零依赖，689 行，无框架负担 |
| 样式 | 原生 CSS + 设计 token | 无预处理器，避免额外构建步骤 |

运行时依赖只有 `maplibre-gl` 一个。

### 5.2 性能优化

**① 静态资源 gzip。**

部署后实测发现首屏要等 1.5 秒，排查后发现服务端**没有任何压缩**——MapLibre 一个包 1.05 MB 直接传输。

加 gzip 后：

| 资源 | 压缩前 | 压缩后 | 降幅 |
|------------------------------|----------------------|-------------------|-------------------|
| maplibre.js | 1,053 KB | 285 KB | -73% |
| index.css | 128 KB | 22 KB | -83% |
| index.js | 24 KB | 11 KB | -55% |

首屏总体积从 1.2 MB 降到 320 KB，Maplibre 加载从 1.5s 降到 0.82s。

压缩结果按 `路径 + mtime` 缓存在内存（LRU 40 条），不重复压；只压文本类资源，图片和字体本身已压缩，再压只是浪费 CPU。

**② 代码分割。**

MapLibre 单独拆 chunk，首屏可并行下载；业务代码与 AI 模块分离。

**③ 长缓存。**

带 hash 的产物用 `immutable` 长缓存，`index.html` 不缓存。

**④ 渲染性能。**

地图逐帧推 zoom 时，`setPaintProperty` 每次都会触发 style 重算。所有 paint 写入前都做差值判重（变化超过 0.004 才写），`moveLayer` 限流 500ms 一次。

这一条是做了性能采样后确认的：我们自己的 JS 只占 9ms / 1354ms，热点全在 MapLibre 与软件渲染的 `readPixels` / `measureText`——**幸好先采样了，否则会对着自己的代码做无效优化**。

### 5.3 密钥与配置安全

- `.env` 在 `.gitignore` 与 `.dockerignore` 双重排除，从未进入 Git 历史
- 前端打包产物中搜不到任何 Key（这是服务端代理存在的全部理由）
- 用户自填的 Key 只存浏览器 localStorage，不经过我们的服务端

### 5.4 部署

单一 Node 进程同时提供静态资源与 API：

```bash
npm run build     # 类型检查 + 打包
npm run serve     # 启动，默认 8080
```

部署包 1.31 MB（11 个文件），只含构建产物与代理层，不含源码与 `node_modules`——云端不需要重新安装依赖和构建。

## 九、实测数据

### 6.1 行程生成

| 城市 | 耗时 | 结果 | 工具定位命中 | 修正轮 |

| 杭州 | 16.6 s | 3 天 12 点 | 12/12 | 1 次 |
| 西安 | 19.7 s | 3 天 14 点 | 14/14 | 1 次 |
| 成都 | 15.7 s | 3 天 12 点 | 12/12 | 1 次 |

| 洛阳 | 17.2 s | 3 天 14 点 | 15/15 | 1 次 |

> 洛阳那次首次定位 15/15 全中，是因为加入了地名降级查询：模型生成的“栾川豆腐宴（老君山店）”带分店名，高德按原名搜不到，剥掉括号后命中。同一份预检在苏州触发过一次——“松鹤楼（山塘街店）”原名 0 条，“松鹤楼”2 条。这类修饰成分在模型输出里非常常见，不处理会白白多跑一轮修正。

“修正轮”指模型编造的 POI 名称在真实地图查不到，被校验器点名要求替换后重新查询。三次测试全部触发，说明这层校验不是摆设。

## 十、局限与展望

### 7.1 当前局限

**① RAG 语料深度不均。** 共 128 条，覆盖 20 个城市：早期 6 个城市每城 8 条，后补的 14 个城市每城 5 条。未收录的城市只能靠通用条目兜底，深度明显弱于已收录城市。

**② 多模态只做了语音。** 语音输入是浏览器原生能力，严格说属于“多模态交互”而非“多模态 AI 理解”。图像理解（比如上传攻略截图自动提取行程）需要视觉模型，当前未接入。

**③ 路线耗时不准。** OSRM 公共服务只有 car 引擎，`foot` / `bike` 三个 profile 返回的 distance 和 duration 完全一样（实测都是 3967m / 301s / 47.4km/h）。距离可信，时长按 4.5km/h 自估，对步行没有参考意义。

**④ 单日行程未做全局最优。** 当前是按“片区聚集”的启发式排序，没有做真正的旅行商问题求解。跨天的最优分配还有优化空间。

### 7.2 后续方向

- **语料扩充**：把 20 个城市的条数拉齐到 8-10 条，同时支持用户贡献（社区共建）
- **视觉理解**：接入多模态模型，支持“上传攻略截图 → 提取成行程”
- **路线引擎自建**：用 OSRM 自建实例，解决公共服务只有 car 引擎的问题
- **行程协同**：多人编辑同一份行程，实时同步

## 十一、社会价值与商业潜力

### 8.1 社会价值

**① 降低了旅行规划的门槛。** 传统方式是在多个平台之间来回跳：小红书找灵感、马蜂窝看攻略、地图查路线、备忘录记行程。一个页面内完成闭环，对不擅长做攻略的人价值明显。

**② 数据基础设施的民主化。** 项目全链路使用开源/免费数据（OpenStreetMap、OSRM、NASA、Esri、OpenFreeMap），没有依赖任何付费地图服务。这意味着**个人开发者和小团队也能做出接近商业水准的地图应用**，不必先付一笔地图授权费。

**③ 信息可信度。** 大模型编造地点是当前 AIGC 的普遍问题。本项目通过“工具核实 + 校验 + 修正”的工程手段把可信度拉到可用水平，这个思路可以迁移到其他需要真实地理约束的场景（如物流、外勤、本地生活）。

### 8.2 商业潜力

**目标市场**：中国自由行市场持续增长，用户对“可执行行程”的需求明确，但现有产品多停留在内容推荐层面。

**竞品差异**：

| 产品 | 形态 | 与本项目的差异 |
|-----------------------------|--------------|-----------------------------------------------|
| 马蜂窝 | 攻略社区 | 内容为主，不生成可执行路线 |
| 小红书 | 灵感社区 | 碎片化，需用户自行整理 |
| 各类 AI 旅行助手 | 文本建议 | 不核实坐标，不连真实道路 |

**核心壁垒**：不是模型能力（各家都能调），而是**地理数据的工程化处理**——坐标系的统一、OSRM 吸附的处理、工具链的降级设计。这些是踩过坑才知道的东西。

**变现路径**：

1. **订阅制**：免费版每天 3 次生成，付费版无限次 + 多方案对比 + 导出 PDF
2. **佣金分成**：行程中的餐厅、酒店、门票接入预订链接
3. **API 输出**：把“行程生成 + 坐标核实”能力封装成 API，供给 OTA、酒店、本地生活平台
4. **B 端定制**：为文旅局、景区做定制版路线规划工具

**成本结构**：单次生成的模型成本约 0.01-0.02 元（DeepSeek 定价），地理编码在免费额度内。订阅定价 9.9 元/月即可覆盖成本并有盈余。

## 十三、附：开发过程中解决的主要问题

按时间顺序，记录几处有代表性的排查过程。

| 问题 | 表面现象 | 真实原因 |
|------------------------|--------------------------|----------------------------------------|
| 生成行程卡住不动 | 按钮转圈、进度条挂着 | 一个变量从未声明，`ReferenceError` 发生在 `try` 之外，`finally` 也被跳过，UI 永久锁死 |
| 生成要等 3-5 分钟 | 点了很久才出结果 | `stream: false` + `max_tokens: 8192`，必须等全部生成完才返回 |
| 点位飘在轨迹外 | 缩小还行，放大偏移 | 切视图时旧轨迹未清 + 图钉热区被撑成 592px |
| 点和线根本不连 | 圆点孤立在线外 | OSRM 把坐标吸附到最近道路，偏远地区偏差 350-400 米 |
| 世界模型搜索不可达 | 提示“搜索服务不可达” | 该路径仍在直连 Photon，而 Photon 在国内被 DNS 污染 |
| 部署后页面空白 | 部署成功但打开是白页 | 产物目录叫 `dist`，被托管平台当作构建产物排除 |
| 线上 API 全部 403 | 本地正常，线上失败 | 健康探测写了 `credentials: 'omit'`，平台靠 cookie 鉴权 |
| 首屏 1.5 秒 | 感觉慢 | 服务端没有 gzip，1 MB 直传 |

这份清单本身也是项目的技术资产——它记录了一个真实的工程系统从“能跑”到“能交付”之间，究竟隔着多少具体的问题。
